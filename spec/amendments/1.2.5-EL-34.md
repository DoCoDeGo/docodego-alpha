# Amendment EL-34 → 1.2.5

*An amendment scaffold for The launch gate (laws/34-the-launch-gate.md). It changes nothing
by itself: the law file, the version stamp, and the log move only when
this amendment is signed and accepted.*

## What changed

The founder-signed paragraph's "who" parenthetical — since 1.2.4:

> who (a typed identifier or handle, recorded verbatim; an identifier
> the engine derives from the environment is recorded as a versioned
> fingerprint of it, never as it stands)

becomes:

> who (a typed identifier or handle, recorded verbatim; an identifier
> the engine derives from the environment is recorded as a versioned
> reversible encoding of it, never as it stands)

The honest-limit sentence added in 1.2.4:

> A fingerprinted identifier is privacy, not anonymity: it resists a
> stranger's lookup, not a determined guesser who already suspects the
> environment.

becomes:

> An encoded identifier is concealment from the casual read, not
> cryptography: it reads plainly to whoever asks the CLI, and a reader
> who declines the CLI can reverse it in one step — it hides the
> identity from a scan, not from an investigator.

No severity change, no duty change; the tiers stay strict
(launch-passed first, one signature per act) and the attestation
sentence stands untouched. Descriptive, not normative: the law's
conformance paragraph may name the mechanism it now enforces (a typed
identifier verbatim; a derived environment identifier as
`enc:v1:<base64>`, revealed on demand by `docodego whoami --decode`).

## Why

The founder's ruling of 2026-11-09 (recorded verbatim in the record's
cycles log, cycle 8, unit 530): "Signing it with a machine has no
meaning if others cannot tell who signed it. I think this whole
signing process needs to have a rethink. Everyone should be able to
see everyone else work within a team. My main concern was having
plaintext name or system name in GitHub commits. encoding seems to be
perfectly fine to hide the identity and only reveal it when needed. We
only need to make it difficult enough to identify someone without
DoCoDeGo CLI." The 1.2.4 fingerprint made the record's own signer a
stranger to their record — an opaque `fp:v1:<hex>` told nobody who
signed. The ruled bar is different: the file must not read a person's
name in the clear (the GitHub-exposure concern), and the team must be
able to see who signed — the CLI reveals on demand, and the difficulty
bar without the CLI is a casual read, not an investigation. The engine
lands the mechanism in the same unit (payload v27): standard base64 of
the derived identifier, version-tagged `enc:v1`, decoded by
`docodego whoami --decode <value>`; the scrypt fingerprint and its
salt-creation leave the sign path; `--name`, `--system`, `--yes`, and
the one-signature rails are byte-for-byte untouched.

## What risk it answers

The named risk: plaintext names or system names exposed on public
GitHub — the encoding removes the clear text from the stored form, so
a scan of the file names nobody. The visibility gain: a team member
reading a signature can ask the CLI who signed — the accountability
tier becomes legible to the team it serves. The trade, named openly:
the 1.2.4 fingerprint was salted per record, so the same environment
was unlinkable across records; the encoding is deterministic
everywhere — the same environment carries the same token in every
record, so cross-record correlation is possible in principle. That
unlinkability is what the visibility ruling spends. And the honesty
limit holds in both directions: the encoding hides a name from a
casual scan, not from an investigator — the record never claims
otherwise. Records signed before this version keep their `fp:v1` rows
as recorded — append-only, no scrubbing — and the committed salt file
stays as their historical key; `fp` rows refuse decoding (one-way by
design), `enc` rows decode on request.
